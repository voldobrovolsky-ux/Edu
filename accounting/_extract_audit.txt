A. Executive Summary
Общий уровень соответствия: низкий относительно целевой модели (вложенная «Бухгалтерия», раздельные сценарии родитель/ученик, жёсткое ACL, полнота экранов, отсутствие критичного хардкода). Текущая реализация — рабочий MVP: JSON-файловые сторы, payroll preview/периоды, compensation engine с UI у админов, тяжёлая «Бухгалтерия» одной страницей.
Архитектура: нет реляционной БД и миграций; данные — JSON в apps/api/data/*.json. Роутинг фронта без role-guard на уровне PrivateRoute (только авторизация). Часть API читает конфигурацию компенсаций без ограничения роли — критичный риск утечки.
UX / навигация: сайдбар плоский; «Настройка расчёта» отдельным верхнеуровневым пунктом для ролей с compensation_engine; нет вложенности «Бухгалтерия → …», нет waterfall-раскрытия подменю, нет отдельного маршрута «Центральный Банк», нет «Мои финансы» у родителя/ученика.
Роли: backend payroll/analytics в целом сужает превью учителя до себя; sysadmin в коде приравнен к руководству по payroll/engine (против требования «не автоматически неограниченно»). Родитель/ученик не получают финансовых разделов в меню, но могут попасть на утечечные GET API, если узнают эндпоинты.
Хардкод: маппинги веток кандидатов, лимиты очков, fallback engine и seed JSON — частично в коде/файлах, без полной админской редактируемости «всего» через UI.
Готовность к инкрементальному исправлению: высокая для UI/роутинга; средняя для ACL (точечные правки роутов); для «всё редактируемо из UI + аудит + версии» потребуется опорная модель данных (не только JSON-файлы).

E. Navigation Audit
Текущая структура: плоский список секций, каждая ведёт на /section/{id}.
Целевая: родитель «Бухгалтерия» с дочерними: «Настройки расчетов», «Аналитика», «Центральный Банк».
Подменю: отсутствуют; используются только переходы на страницы.
Дубли: смысл «аналитики зарплат» раздроблен между AnalyticsPage и AccountingPage.
Role-aware rendering: меню корректно не показывает accounting/engine родителям/ученикам; но API-уровень не повторяет те же ограничения.
Direct URL bypass: возможно открыть маршруты/получить данные, полагаясь только на auth, без проверки роли.

I. Safe Implementation Strategy
Начать с усиления ACL и закрытия критичных GET (без изменения UI).
Затем перестроить сайдбар и роутинг (nested accounting).
После этого заняться разнесением продуктов для родителей/учеников.
Отложить перенос hardcode в конфиг, пока не стабилизирован техстандарт и не добавлен сам DOCX в репозиторий.
Каждый этап сопровождать документированием в отдельном CHANGELOG/разделе.
